# 灵感是独立集合，采用是引用而非移动

零散的想法（梗、台词、桥段、转折）在写下来的时候往往还没有归属，硬塞进事件里会逼设计者提前决定
它属于哪一章、哪个角色，而这个决定正是他此刻不想做的。所以工程里给它们一个独立的顶层集合 `ideas`，
与 `events` 平级：灵感不落在画布上，不占用逻辑时间，也不属于任何轴。它只有一个原文 `text`，
以及可选的标题、类型、标签与关联实体。

**原文永不被覆盖。** 灵感的 `text` 是不可变的原始记录，AI 的扩写与改写分别写进 `expansion` 与
`variants`。小想法常常妙在当初的措辞，被润色一遍就没了味道；只要原文还在，任何扩写都只是可丢弃的
尝试。这与工程里"文件即数据源、任何改动都可撤销"的取向一致。

**采用是引用，不是搬运。** 灵感被写进剧情后不消失，而是记下 `usedBy` 并把状态转为 `used`。
同一条梗可能先用在一处，日后又在别处呼应；如果采用即删除，这种复用关系就断了。反过来，
事件也不需要保存"来自哪条灵感"，因为那只是 `usedBy` 的反向读法，重复存储会制造两份可能不一致的事实。

**合并是软合并。** 把多条灵感合成一条时，新建一条汇总灵感并在其上记录 `mergedFrom`，
被合并的那几条标记为 `merged` 并记下 `mergedInto`，但不从集合里移除。合并往往是"这几条其实是一个东西"
的判断，而判断可能反悔；保留来源既让合并可追溯，也允许日后拆开。这和章节归属由逻辑时间派生
（ADR-0004）是同一个立场：能被推导出来的关系，不要固化成会过期的字段。

**灵感视图不是投影。** 角色视图与地点视图是对时间线的过滤呈现（ADR-0004），而灵感根本没有时间位置，
无法投影。它是一块独立的卡片墙，不共用画布渲染管线。把两者混为一谈会让 `viewMode` 的语义变得含糊，
所以这里明确区分：前三个视图是同一份空间数据的三种看法，灵感视图是另一份数据的唯一看法。
